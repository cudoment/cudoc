# cudoc 가이드

[English](./README.md) | **한국어** · [프로젝트 홈](../README.ko.md)

가이드가 작업 흐름을 알려 준다면, [API 레퍼런스](./api-reference/README.ko.md)는 시그니처와 기본값과 계약을 담습니다.

## 사이트에 설치하기

각 가이드는 설치, 설정, 수집 연결, 빌드 순으로 번호를 매긴 절차입니다. 모든 단계가 그대로 복사해 쓸 수 있는 명령이나 파일이라, 직접 따라 하셔도 되고 코딩 에이전트에게 넘기셔도 됩니다. 각 가이드는 그렇게 설정한 다음 무엇을 쓸 수 있는지 정리한 표와, 그 호스트에서 알아 둘 점으로 끝납니다.

| 사용 중인 사이트       | 가이드                             |
| ---------------------- | ---------------------------------- |
| **Next.js**            | [Next.js →](./next.ko.md)          |
| **Docusaurus**         | [Docusaurus →](./docusaurus.ko.md) |
| **Nextra**             | [Nextra →](./nextra.ko.md)         |
| **VitePress**          | [VitePress →](./vitepress.ko.md)   |
| **Eleventy**           | [Eleventy →](./eleventy.ko.md)     |
| **아직 생성기가 없음** | [HTML 내보내기 →](./export.ko.md)  |

문법 확장만 쓰실 거라면 호스트 설정에서 끝납니다. 문서 임베딩은 사이트를 빌드하기 전에 수집이 먼저 돌아야 하는데, 각 가이드가 그 경계를 표시해 둡니다.

## 지원 버전

cudoc에는 Node.js 20 이상이 필요하며 모든 패키지는 ESM입니다. 아래 표는 호스트마다 cudoc의 모든 변경을 검증하는 버전, cudoc이 지원하는 버전, 어댑터가 npm에 선언한 피어 범위를 보여 줍니다.

| 호스트     | 검증한 버전                        | 지원 범위                            | 선언한 피어 범위                                              |
| ---------- | ---------------------------------- | ------------------------------------ | ------------------------------------------------------------- |
| Next.js    | Next.js 16.3.8, `@next/mdx` 16.3.8 | Next.js 16.3 이상의 16.x             | 호스트 피어 없음: `cudoc-remark`는 remark 플러그인입니다      |
| Docusaurus | Docusaurus 3.10.2                  | 3.10 이상의 3.x                      | `@docusaurus/core` `^3.10.0`                                  |
| Nextra     | Nextra 4.6.0, Next.js 15.5.25      | Next.js 15에서 Nextra 4.6 이상의 4.x | 호스트 피어 없음: `cudoc-nextra`는 remark 플러그인 모음입니다 |
| VitePress  | VitePress 1.6.4                    | 1.6.4 이상의 1.x                     | `vitepress` `^1.6.4`, `markdown-it` `^14.1.0`                 |
| Eleventy   | Eleventy 3.1.6                     | Eleventy 3.1 이상의 3.x              | `@11ty/eleventy` `^3.1.0`, `markdown-it` `^14.1.0`            |

**검증한 버전**은 [실행 가능한 예제](../examples/README.md)가 잠가 둔 정확한 버전이며, 지속적 통합이 이 버전으로 빌드하고 검사하고 각 가이드를 그대로 따라 해 봅니다. **지원 범위**에 드는 버전에서 생긴 문제는 결함으로 받아서 고치지만, 실제로 실행해 보는 버전은 검증한 버전뿐입니다. 선언한 피어 범위는 지원 범위가 시작하는 버전에서 시작합니다. 따라서 어댑터가 호스트를 피어로 선언한 경우, npm은 지원하는 호스트 버전 옆에만 어댑터를 설치합니다. 사이트가 선언한 범위 안에서 호스트를 지원 버전으로 올리거나, Docusaurus 3.5에서처럼 `ERESOLVE`로 설치를 거부합니다.

호스트 버전에 따라 달라지는 연동 조건은 다음과 같으며, 호스트를 올릴 때 다시 확인할 부분입니다.

- **Docusaurus.** [수집기](./docusaurus.ko.md#5단계--수집기-추가)는 공개 API가 아닌 내부 모듈 `@docusaurus/mdx-loader/lib/processor.js`에서 Docusaurus 자체 MDX 프로세서를 가져와 실행합니다. 라이브러리 로더는 webpack 규칙이며 `include`에 콘텐츠 디렉터리를 적어야 합니다.
- **Nextra.** 어댑터가 Nextra에 플러그인 함수를 넘기는데 Turbopack은 이를 직렬화하지 못하므로, 사이트는 webpack으로 빌드하고 서비스하며 [라이브러리 로더](./nextra.ko.md#4단계--임베드-플러그인과-라이브러리-로더-추가)도 webpack에 등록합니다.
- **Next.js.** 플러그인 이름을 문자열로, 옵션을 JSON으로 쓰므로 Turbopack과 webpack 모두에서 동작하며, 두 번들러를 모두 검증합니다.
- **VitePress 개발 서버.** VitePress 1은 Vite 5에서 실행되는데, Vite 5의 개발 서버에는 Windows에서 `server.fs.deny`를 우회할 수 있는 문제를 비롯한 보안 공지가 나와 있으며 이를 고친 Vite 5 릴리스는 없습니다. 이 공지는 `vitepress dev`에만 해당하고 `vitepress build`가 만드는 사이트에는 해당하지 않습니다. 개발 서버는 자기 컴퓨터나 신뢰할 수 있는 네트워크에서만 실행하십시오. 아직 보고되는 공지와 남겨 둔 이유는 [예제 문서](../examples/README.md#build-an-example)에 정리했습니다.
- **VitePress와 Eleventy.** 플러그인은 설정을 평가할 때 불러온 라이브러리를 계속 들고 있으므로, 다시 수집한 뒤에는 개발 서버를 재시작합니다([VitePress](./vitepress.ko.md#6단계--빌드-전마다-수집-실행), [Eleventy](./eleventy.ko.md#7단계--빌드-전마다-수집-실행)).

cudoc은 유의적 버전을 따르며, 여덟 패키지가 모두 같은 버전을 씁니다. 호환을 판단하는 대상은 [API 레퍼런스](./api-reference/README.ko.md)가 문서화한 범위입니다. 공개 import와 그 시그니처, 옵션과 기본값, Markdown 문법, `cudoc`과 `cudoc-export` 명령, 저장 형식이 여기에 해당합니다. 1.0.0 전에는 수 버전이 이 범위를 모두 유지하고, 부 버전은 이 범위를 바꿀 수 있으며 무엇을 고쳐야 하는지는 [릴리스 노트](./release-notes.ko.md)에 적습니다. 패키지가 export하지 않는 모듈은 처음부터 이 범위에 들지 않습니다.

결함은 [github.com/cudoment/cudoc/issues](https://github.com/cudoment/cudoc/issues)에 보고해 주십시오. 신고 양식이 호스트와 그 버전, cudoc 버전, 문제를 보여 주는 가장 작은 문서를 묻습니다.

## `.md`와 `.mdx` 선택

**cudoc의 모든 기능은 두 형식에서 똑같이 동작합니다.** 앵커와 배지, 콜아웃, 표 셀 안의 목록은 어느 호스트에서든 어느 형식에서든 평범한 HTML 요소로 컴파일됩니다. 그래서 cudoc 때문에 `.mdx`를 써야 하는 경우는 없습니다. 무엇을 쓰실지가 기준이 됩니다. `.mdx`는 **직접 만드신 React 컴포넌트**를 쓰기 위한 형식입니다.

형식은 프로젝트가 아니라 **파일마다, 확장자로** 갈립니다. 수집도 호스트와 똑같이 확장자를 읽으므로 한 디렉터리에 두 형식을 섞어 두셔도 됩니다.

| 사용 중인 사이트 | `.md` | `.mdx`                 | 결정 방식                             |
| ---------------- | ----- | ---------------------- | ------------------------------------- |
| Next.js          | 가능  | 가능                   | `@next/mdx` 옵션의 `format: "detect"` |
| Docusaurus       | 가능  | 가능                   | `markdown: { format: "detect" }`      |
| Nextra           | 가능  | 가능                   | `mdxOptions`의 `format: "detect"`     |
| VitePress        | 가능  | 불가                   | markdown-it에는 MDX 파서가 없음       |
| Eleventy         | 가능  | 불가                   | markdown-it에는 MDX 파서가 없음       |
| HTML 내보내기    | 가능  | 컴포넌트별 렌더러 필요 | 컴포넌트 이름을 해석할 등록부가 없음  |

markdown-it 계열 두 호스트는 읽지 못하는 `.mdx` 파일을 어설프게 넘기지 않습니다. 수집이 이유를 말하고 멈춥니다.

```
cudoc-vitepress: markdown-it hosts compile Markdown .md documents, not React .mdx
```

정책이 아니라 파서의 한계입니다. 그 호스트에서도 컴포넌트를 쓰는 길은 따로 있습니다. VitePress는 `.md` 안에 바로 쓴 Vue 컴포넌트를 렌더링하고, cudoc은 그중 정적인 형태를 정규화합니다. → [VitePress](./vitepress.ko.md#vitepress에서-알아-둘-점)

### 컴포넌트를 쓰면 무엇을 감수하게 되는가

컴포넌트는 등록된 곳에서만 렌더링됩니다. 그 컴포넌트를 가진 문서 안에서는 아무 문제가 없다가, 임베드가 그 절을 다른 문서로 복사하는 순간부터 문제가 됩니다. HTML 내보내기에는 그 이름을 찾아볼 등록부가 없기 때문입니다. [`cudoc check`](./check.ko.md#unportable-component-경고)가 이걸 내보내기 시점까지 미루지 않고 검사 시점에 알려 줍니다.

그래서 지키실 기준은 하나뿐입니다. **다른 문서가 임베드하는 절만 Markdown으로 두시고**, 나머지 자리에는 컴포넌트를 마음껏 쓰시면 됩니다.

## 다루는 범위

cudoc이 맡는 일은 Markdown 문법 정규화, 문서 간 임베딩, AST 투영, HTML 생성입니다. 설정은 사이트를 만드는 쪽의 몫이고, 작성자는 평범한 Markdown과 cudoc 표기만 쓸 뿐 cudoc 컴포넌트를 가져오거나 등록하지 않습니다.

네이티브 문법은 각 가이드에 적힌 형태까지만 지원합니다. 아무 호스트 플러그인이나 동적 컴포넌트가 저절로 이식 가능해지지는 않습니다. 내용이 실행 시점 상태에 달린 컴포넌트는 임베드로도, 내보낸 HTML로도 옮겨 가지 못합니다. 링크를 실시간으로 감시하는 기능은 없습니다. 수집은 `cudoc collect --watch`로 변경마다 반복되며, [수집 설정](./embedding.ko.md#문서-수집-설정)에 설명합니다.
